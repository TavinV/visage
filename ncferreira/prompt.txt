## Contexto

Você vai construir o **frontend de produto** do VisageX — um SaaS multi-tenant de chamada escolar por reconhecimento facial — dentro do diretório `frontend/` (Next.js 14, App Router, TypeScript, Tailwind, já inicializado). Hoje esse diretório só tem a **landing page de marketing** (`src/app/page.tsx` + `src/components/landing/*`, paleta azul "brand-*"). Você vai adicionar, **ao lado** dela, sem quebrá-la, a aplicação autenticada: login, console do super admin e console do tenant, com CRUDs básicos.

**Não existe ainda logo própria do Visage.** Use temporariamente a marca (águia) da Flauzino — a software house que constrói o produto — como ícone/mark, mas o nome do produto exibido continua sendo **"Visage"**, nunca "Flauzino". Trate isso como um placeholder de marca White-label temporário, não como rebranding do produto.

## Fundação visual obrigatória

**Namespace isolado, para não colidir com a landing:** a landing usa `brand-*` (azul) no Tailwind e a paleta neutra padrão do Tailwind (`slate-*` nativo). O design system da Flauzino também define um `--slate-*` só que com **valores diferentes** (mais frio, tendendo a navy). Para não colidir nem confundir, estenda o `tailwind.config.ts` com um namespace próprio, por exemplo `flauzino: { navy: {...}, ink: {...}, slate: {...}, accent: {...}, success: {...}, warning: {...}, danger: {...} }`, mapeando 1:1 para os valores em `design-system/tokens/colors.css` (pode usar `var(--navy-900)` etc. como valor do Tailwind, ou os hex diretos — mantenha rastreável ao token de origem). Classes resultantes: `bg-flauzino-navy-900`, `text-flauzino-slate-500`, `border-flauzino-slate-200`, etc. A landing continua usando `brand-*` normalmente.

**Tipografia:** Poppins já está carregada (`--font-poppins`) — reaproveite. O design system pede **IBM Plex Mono** para dados/IDs/timestamps (a landing usa JetBrains Mono como `--font-mono`) — carregue IBM Plex Mono via `next/font/google` adicionalmente (variável própria, ex. `--font-mono-ds`) e use só dentro da área autenticada, sem alterar o `--font-mono` global que a landing consome.

**Disciplina de peso:** body 400, labels/UI 500, headings 600, display 700 (raro). Eyebrows em uppercase com `tracking-wide`/`0.14em`, nunca o corpo do texto.

**Grid de 4px, raios contidos** (`--radius-md` 8px como padrão, `--radius-lg` 12px para painéis grandes — nada de "tudo em pill"), **sombras frias com tom navy** (nunca preto puro), foco sempre visível (anel de 3px, `--ring-focus`). Sem glassmorphism, sem gradientes decorativos, sem neon.

**Ícones:** Lucide (`lucide-react`, já instalado) — stroke 1.5–2px, nunca preenchido, `currentColor`.

**Logo:** copie `design-system/assets/flauzino-logo.svg` (esse é o arquivo real da marca — note que o `readme.md` do design system referencia `flauzino-mark.svg`, que **não existe no disco**; use o `.svg` real) para `frontend/public/`. Construa um componente `Logo` próprio (não reaproveite `Logo.jsx` do design system tal qual — ele tem `"Flauzino"` fixo como wordmark). Seu componente deve aceitar `variant="mark"|"lockup"|"stacked"`, renderizar a águia como mark e **"Visage"** como wordmark (peso 600, mesma lógica visual do `Logo.jsx` de referência), com tagline opcional em uppercase abaixo (ex. "CONSOLE", "PAINEL ADMINISTRATIVO").

**Componentes que faltam no design system e você precisa desenhar do zero, seguindo os mesmos princípios visuais (navy authority, accent azul único, cards brancos com hairline + sombra navy suave):** `Select`, `Table` (com estados de loading/vazio/erro), `Modal`/`Dialog` (para confirmação de exclusão e formulários), `Toast`/notificação de sucesso-erro, `Pagination`, `EmptyState`, `Skeleton`/spinner, `Textarea`. São essenciais para os CRUDs e não existem em `design-system/components/`.

Recomenda-se instalar `react-hook-form` + `zod` para formulários (já é o padrão descrito em `.claude/development.md` para este projeto) e algo leve para data-fetching com cache/mutação (ex. `@tanstack/react-query`) — os CRUDs são intensivos em list/create/update/delete e um wrapper de fetch cru vai gerar muito código repetido.

## Arquitetura da aplicação autenticada

- **API client** (`src/lib/api.ts`): wrapper de `fetch` apontando para `NEXT_PUBLIC_API_URL` (default `http://localhost:3000`), injeta `Authorization: Bearer <accessToken>`, e num 401 tenta **uma vez** `POST /auth/refresh` com o refreshToken salvo e repete a request original (padrão já descrito em `.claude/development.md`). Se o refresh falhar, desloga e redireciona para `/login`.
- **AuthProvider/context:** guarda `accessToken` em memória (state), `refreshToken` em `localStorage`, e os dados do usuário (`{id, email, name, role}` — vem em `POST /auth/login` → `{ data: { accessToken, refreshToken, expiresIn, user } }`). **Atenção:** a resposta de login **não** inclui `tenantId` no objeto `user` — o backend extrai o tenant do JWT em cada request, o frontend nunca precisa dele diretamente, só do `role` para decidir navegação.
- **Guarda de rotas por grupo:** como os tokens vivem no client (não em cookie), proteja por layout, não por Next middleware. Sugestão de estrutura:
  - `src/app/login/page.tsx` — login único; após autenticar, redireciona para `/admin` se `role === "super_admin"`, senão para `/dashboard`.
  - `src/app/(super-admin)/admin/*` — layout que exige `role === "super_admin"`, senão redireciona.
  - `src/app/(tenant)/dashboard/*` — layout que exige role em `["admin","manager","teacher"]` (ajuste por tela conforme a tabela de permissões abaixo), senão redireciona.
- **Shell:** Sidebar + Topbar fixos (baseados em `Sidebar.jsx`/`Topbar.jsx` do Sentinel), com dois conjuntos de itens de navegação — um para o console do super admin, outro para o console do tenant — e avatar/menu do usuário com logout.

## Escopo, em ordem de prioridade

1. **Fundação:** tokens no Tailwind, fontes, `Logo`, componentes base (Button, Input, Select, Textarea, Checkbox, Switch, Card, Badge, Avatar, Table, Modal, Toast, Pagination, EmptyState, Skeleton).
2. **Auth:** api client com refresh automático, `AuthProvider`, página `/login` (painel de marca + formulário, no estilo do `Login.jsx` do Sentinel), guardas de rota.
3. **Shell do app:** Sidebar + Topbar responsivos, navegação role-aware.
4. **Console do super admin** (`/admin`):
   - Dashboard/overview (contagem de tenants, planos ativos — pode ser derivado das listagens, sem endpoint de stats dedicado).
   - CRUD de **planos** (`Plan`: nome, `maxClasses`, `priceMonthly`, `isActive`).
   - CRUD de **tenants** (nome, documento, tipo de instituição, plano, status) + ações: ativar, desativar, cancelar, **rotacionar chave (DEK)**.
   - Tela de **logs de reconhecimento globais** (somente leitura, tabela filtrável).
   - Widget/tela de **saúde da engine** (`GET /admin/health`).
   - Tela de **conta** com ação de rotacionar a própria senha do super admin.
5. **Console do tenant** (`/dashboard`):
   - Dashboard/overview (contadores simples: usuários, turmas, dispositivos ativos).
   - CRUD de **usuários** (nome, email, role, documento/CPF, matrícula) — inclua badge de `facialStatus` e, na tela de detalhe de um aluno: botão **"Gerar QR Code de cadastro"** (chama `POST /students/:id/enrollment-token`, mostra o token retornado — pode renderizar como QR Code client-side com uma lib como `qrcode.react`, já que isso não usa câmera, é só gerar uma imagem a partir de uma string), status do token, botão de revogar, e as ações LGPD (revogar consentimento, excluir dados).
   - CRUD de **localizações/salas** (`Location`: nome, endereço, ativo).
   - CRUD de **dispositivos/totens** (`Device`: fingerprint, label, localização, ativo) — ao criar, o backend gera a API key uma única vez; exiba-a claramente com um botão de copiar, avisando que não será mostrada novamente.
   - CRUD de **períodos acadêmicos** (`AcademicPeriod`: nome, início, fim, ativo).
   - CRUD de **cursos/matérias** (`Course`: nome, período acadêmico).
   - CRUD de **turmas** (`Class`: nome, curso, professor, sala/localização, `totalClassesPlanned`).
   - Gestão de **matrículas** (`ClassEnrollment`: aluno ↔ turma) — pode ser uma sub-tela dentro do detalhe da turma (lista de matriculados + adicionar/remover).
   - **Sessões de chamada** (`ClassSession`): listagem com filtro por status/turma, abrir nova sessão (turma + `classesWorth`), fechar sessão. **Não** construa aqui um painel de presença em tempo real via SSE nem qualquer visualização de câmera — isso fica para uma fase futura.
   - **Relatórios**: frequência por turma (`GET /attendance/reports/frequency`), histórico de um aluno (`GET /attendance/reports/student/:id`), resumo por turma do aluno (`GET /attendance/reports/student/:id/summary`).
   - **Auditoria**: lista de `recognition_logs` do tenant com filtros (data/status/usuário); ao clicar num log com `fraudFrameExists=true`, abra um modal que busca `GET /audit/frames/:id` **como blob autenticado** (`fetch` com header `Authorization`, depois `URL.createObjectURL`) — um `<img src="...">` direto não envia o header e vai falhar com 401.
   - **Configurações do tenant** (`GET/PATCH /tenant-settings`) — formulário com os thresholds e toggles (ver schema abaixo).

## Referência de API verificada (backend real, não o doc aspiracional)

Base: `NEXT_PUBLIC_API_URL` (backend roda em `http://localhost:3000` por padrão — `config.ts`/`.env.local`). Toda resposta de lista é `{ data: T[], pagination: { total, page, limit, totalPages } }`; recurso único é `{ data: T }`; erro é `{ error: string, code: string }` (validação Zod também inclui `issues: [{path, message}]`).

| Domínio | Rotas | Roles |
|---|---|---|
| Auth | `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout` | público |
| Planos | `GET/POST /plans`, `GET/PATCH/DELETE /plans/:id` | GET público (autenticado); mutações `super_admin` |
| Tenants | `GET/POST /tenants`, `GET/PATCH /tenants/:id`, `POST /tenants/:id/{activate,deactivate,cancel,rotate-key}` | `super_admin` |
| Tenant settings | `GET /tenant-settings` (qualquer autenticado), `PATCH /tenant-settings` | PATCH `admin`/`super_admin` |
| Usuários | `GET/POST /users`, `GET/PATCH/DELETE /users/:id`, `PUT /users/:id/change-password`, `POST /users/:id/revoke-consent`, `DELETE /users/:id/data` | `admin`/`super_admin` (revoke-consent também aceita `manager`) |
| Localizações | `GET/POST /locations`, `GET/PATCH/DELETE /locations/:id` | `admin`/`super_admin` |
| Dispositivos | `GET/POST /devices`, `GET/PATCH/DELETE /devices/:id` | `admin`/`super_admin` |
| Períodos acadêmicos | `GET/POST /academic-periods`, `GET/PATCH/DELETE /academic-periods/:id` | `admin`/`super_admin` |
| Cursos | `GET/POST /courses`, `GET/PATCH/DELETE /courses/:id` | `admin`/`super_admin` |
| Turmas | `GET/POST /classes`, `GET/PATCH/DELETE /classes/:id` | `admin`/`super_admin` |
| Matrículas | `GET/POST /class-enrollments`, `GET/DELETE /class-enrollments/:classId/:userId` | `admin`/`super_admin` |
| Sessões de chamada | `GET/POST /class-sessions`, `GET/PATCH /class-sessions/:id`, `POST /class-sessions/:id/close`, `GET /class-sessions/:id/records` | `admin`/`super_admin` (records também `manager`/`teacher`) |
| Cadastro biométrico (token) | `POST/GET/DELETE /students/:id/enrollment-token` | `admin`/`manager`/`super_admin` |
| Relatórios | `GET /attendance/reports/frequency?class_id&period_id`, `GET /attendance/reports/student/:id`, `GET /attendance/reports/student/:id/summary` | `admin`/`manager`/`teacher`/`super_admin` |
| Auditoria | `GET /audit/recognition-logs?date&status&user_id`, `GET /audit/frames/:recognitionLogId` | list: `admin`/`manager`/`super_admin`; frame: só `admin`/`manager` |
| Admin global | `GET /admin/recognition-logs`, `GET /admin/health`, `POST /admin/rotate-password` | `super_admin` |

`Plan { id, name, maxClasses, priceMonthly, isActive }` · `Tenant { id, name, document?, institutionType: "school"|"university", status: "trial"|"active"|"suspended"|"cancelled", timezone }` · `User { id, name, email?, role: "admin"|"manager"|"teacher"|"student", document?, enrollmentCode?, facialStatus: "none"|"consent_given"|"registered"|"consent_refused"|"revoked", status }` · `TenantSettings { recognitionThreshold, livenessThreshold, livenessEnabled, staticPixelThreshold, allowManualOverride, preAttendanceEnabled, preAttendanceWindowMin, individualCheckoutEnabled, saveFraudFrames, fraudRetentionHours, enrollmentTokenExpiryHours, requireConsentBeforeFacial, enrollmentMultiFrameCount, livenessThresholdEnrollment }`.

## Fora de escopo — não construir nesta tarefa

- Qualquer tela que peça acesso à câmera (`getUserMedia`), capture frames ou exiba vídeo ao vivo — isso inclui o **totem PWA** completo (`/totem/*`), a tela de captura multi-frame do cadastro biométrico, e qualquer painel de "reconhecimento ao vivo".
- Painel de presença em tempo real via SSE (`GET /class-sessions/:id/stream`, `GET /device/stream`).
- Não recrie o widget decorativo de câmera do `Dashboard.jsx` do Sentinel (`.sx-cam`, feed falso) — se quiser um cartão de "monitoramento" no dashboard, use contadores/ícones estáticos, não uma simulação de câmera.
- Checkout individual, ajuste manual de presença — endpoints ainda não existem no backend.

## Antes de começar (setup local)

- O backend só cria o `super_admin` no boot se **já existir pelo menos um plano ativo** no banco (`bootstrapSuperAdmin` busca `plan.findFirst({isActive:true})` e aborta silenciosamente se não achar). Rode `cd backend && npm run seed` (cria 3 planos) **antes** de subir o backend pela primeira vez.
- Credenciais de teste do super admin: veja `SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD` em `backend/.env.local`.
- O backend tem `CORS_ORIGIN=http://localhost:3001,http://localhost:3000` — rode o frontend na porta **3001** (`next dev -p 3001` ou `PORT=3001` em `frontend/.env.local`) para evitar colisão de porta com o próprio backend (que também usa 3000 por padrão).
- Defina `frontend/.env.local` com `NEXT_PUBLIC_API_URL=http://localhost:3000`.

## Padrões gerais

- TypeScript estrito, sem `any` implícito.
- Copy em português, tom institucional descrito no `readme.md` do design system (sentence case, sem emoji, sem exclamação, precisão > hype). Rótulos de botão: verbo + objeto ("Criar turma", "Revogar token", não "Criar!").
- Mensagens de erro da API (`{error, code}`) devem ser traduzidas/mapeadas para mensagens amigáveis onde fizer sentido, mas nunca inventar dados que a API não retornou.
- Todo formulário precisa de estado de loading no submit e feedback de sucesso/erro (Toast).
- Toda listagem precisa de estado vazio, estado de erro e paginação (usando o envelope `pagination` retornado).
- Responsivo o suficiente para uso em desktop/tablet (é um console administrativo, não precisa otimizar para mobile pequeno).

## Entregáveis esperados

- Fundação visual (tokens Tailwind + fontes + Logo + componentes base) commitada em `frontend/src/components/ui/` (ou pasta equivalente), reutilizável entre os dois consoles.
- Login funcional contra o backend real.
- Console do super admin e console do tenant navegáveis, com todos os CRUDs listados na seção de escopo funcionando fim a fim contra a API (create/read/update/delete visíveis na tela após a ação).
- Nenhuma tela ou componente que solicite câmera.
- A landing page em `/` continua funcionando exatamente como está.
